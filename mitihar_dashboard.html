Mitihar

Audited 2026‑09‑18
Stage: Cloud Testing / Staging (backend only)
Does Mitihar currently have a live application?
Partially. The FastAPI backend is deployed and publicly reachable on Cloud Run staging at a stable HTTPS URL, backed by a real Cloud SQL database and Redis instance — and it has passed one real load test against that live infrastructure. Neither client app is deployed — the web dashboard's Firebase Hosting project has never been pushed to, and the patient app's build config still contains literal placeholder URLs (STAGING-URL-NOT-DEPLOYED-YET). A teammate can call the API directly, but there is currently nothing they can open and use as "Mitihar."

05Done vs. missing

What's actually done

  • Backend live on Cloud Run staging, real URL, HTTPS
  • Cloud SQL + Memorystore provisioned, private-IP, VPC egress
  • Cloud Scheduler cron replacing in-process APScheduler
  • JWT + cookie auth, Google OAuth, TOTP MFA — all real
  • One successful tuned load test against live infra (Aug 7)
  • Chaos testing confirms fail-open Redis + DB pool recovery
  • CI running lint + unit tests on every push

What's missing

  • Web dashboard never deployed to its own Firebase project
  • Patient app never built — EAS URLs are still placeholders
  • No CI/CD deploy automation — manual script only
  • Horizontal autoscaling never tested
  • No automated, tested Cloud SQL backup/restore
  • Redis transit encryption disabled — self-flagged, unreviewed
  • No monitoring/alerting pipeline in the repo

06Recommended next steps

  1. Reconfirm CI is green and the Cloud Run config still matches the Aug 7 passing setup before trusting existing test evidence.
  2. Fix the broken meal-plan medical-safety check (JSONB key mismatch) — currently masking whether that logic works at all.
  3. Deploy the web dashboard to the already-configured Firebase Hosting project and smoke-test against staging.
  4. Re-run the full load / chaos / E2E suite against current main.
  5. Fix the /meal-plan/week query hotspot identified in the last load test.
  6. Fill in real EAS URLs and ship an internal-distribution build of the patient app.
  7. Only then: formal production-readiness review — monitoring, backups, cost controls, Redis transit encryption.
