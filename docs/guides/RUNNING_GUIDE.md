## 2. COMMON ERRORS & FIXES

| Issue | Solution |
| :--- | :--- |
| **Database Connection Failed** | Ensure Docker Desktop is running and you executed `setup.bat`. |
| **Port 8000 in use** | Find and kill the process: `Stop-Process -Id (Get-NetTCPConnection -LocalPort 8000).OwningProcess` |
| **Import Error** | Re-run `pip install -r requirements.txt` within the active venv. |
| **JWT Invalid** | Ensure `SECRET_KEY` matches in `.env` and tokens haven't expired. |
| **402 Subscription Required** | Patients require an active subscription to generate meal plans (`/api/v1/meal-plan/*`). See testing flows below. |

## 3. TESTING THE API MANUALLY

Use the **Swagger UI** (`/docs`) or `curl` to test endpoints. Testing differs by your access role: **Admin**, **Doctor**, or **Patient**.

### A. Testing as a Patient
Patients are the core users. They can be standalone or connected to a doctor via a subscription code.

**Step 1: Register**
- **Route**: `POST /api/v1/auth/register`
- **Payload**: Provide profile information (`email`, `password`, `weight_kg`, `diet_type`, `region`, etc.)
- **Alternative (Google OAuth)**: Hit `GET /api/v1/auth/google/login` in your browser.

**Step 2: Login**
- **Route**: `POST /api/v1/auth/token`
- **Form Data**: `username=email`, `password=password123`
- *Note: Click the "Authorize" padlock in Swagger at the top right and paste your token so subsequent requests are authenticated.*

**Step 3: Generating a Meal Plan**
- **Requirement**: Must have an active subscription connected to a Doctor! (Otherwise you'll get HTTP 402 from Middlewares).
- **Route**: `POST /api/v1/patients/me/connect-doctor`
  - Paste an active `subscription_code` (generated by a Doctor, see below).
- **Route**: `POST /api/v1/meal-plan/generate`
  - This calls the AI meal generator to create a localized, calorie-restricted meal plan version for the week based on your BMR/TDEE calculations.

**Step 4: Tracking Daily Progress**
- **Route**: `POST /api/v1/progress/log`
- Used to track daily weight changes, steps, and water intake.

---

### B. Testing as a Doctor
Doctors manage patients and their own clinic profiles.

**Step 1: Doctor Login**
- **Route**: `POST /api/v1/auth/doctor/login`
- Use the seeded doctor credentials (or create a new doctor).
  - *Seeded Email*: `testdoctor@mityahar.com` (Check DB for exact seed records).
  - *Password*: `doctor1234`

**Step 2: Generate Subscription Codes**
- **Route**: `POST /api/v1/doctor/subscription-codes`
- **Purpose**: Generates access codes that you provide to patients. When patients use this code, they are linked to you and their subscription becomes active.

**Step 3: Monitor Patients**
- **Route**: `GET /api/v1/doctor/patients`
- **Route**: `GET /api/v1/doctor/patients/{patient_id}/progress`
- *Security Note*: Doctors are strictly isolated via `DoctorIsolationMiddleware`. You can only view details of patients linked to your `doctor_id`.

**Step 4: Clinical Notes**
- **Route**: `POST /api/v1/doctor/patients/{patient_id}/notes`
- Create notes (public to the patient or strictly private/internal for doctor reference).

---

### C. Testing as an Admin
Admins oversee billing metrics, audit logs, and compliance. Admins are secured via JWT *and* IP Whitelisting.

**Step 1: Ensure Your IP is Whitelisted**
- You must either add your IP address `127.0.0.1` to the `admins.allowed_ips` column in the database or disable IP checking in `.env` (if applicable) prior to calling these routes. The `AdminIPWhitelistMiddleware` enforces this.

**Step 2: Login**
- **Route**: `POST /api/v1/auth/admin/login`
- Use the seeded admin credentials.
  - *Email*: `admin@mityahar.com`
  - *Password*: `admin1234`

**Step 3: Admin Actions**
- **Route**: `GET /api/v1/admin/audit-logs`
- View all platform actions across all users for security compliance.
- **Route**: `GET /api/v1/admin/billing-overview`
- See financial tracking across all active subscriptions in the platform.
