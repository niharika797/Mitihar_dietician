# Full retest after the fixes

Run 2026-10-28 on the local Docker rig: API 1 CPU / 1 GB, one worker; Postgres 2 CPU; no Redis; 1,000 synthetic patients. Same rig and same scenarios as `REPORT_1vCPU_API_2vCPU_DB.md` (2026-10-26), current code (all of today's fixes and the habit learning). Nothing real was touched. Script: `rig/run_retest.sh`. Raw numbers: `out_retest/`.

## Load scenarios, old vs new
| Scenario | Old: typical / slowest 5% / slowest 1% | New | Failed old | Failed new |
|---|---|---|---|---|
| Steady 11 req/s, 5 min | 33 / 120 / 180 ms | 22 / 47 / 120 ms | 0 | 0 |
| Ramp 1 to 100 req/s, 10 min | 10 / 56 / 200 ms | 9 / 27 / 120 ms | 436 | 409 |
| 300 patients in 30 s | 150 / 630 / 1000 ms | 86 / 360 / 550 ms | 0 | 0 |
| 300 logins in 5 min | 6 / 220 / 490 ms | 5 / 210 / 480 ms | 0 | 0 |
| 10 doctors reviewing | 22 / 170 / 280 ms | 14 / 52 / 120 ms | 0 | 0 |
| 100 weight logs in 60 s + 50 browsing | 2,100 / 28,000 / 30,000 ms | 9 / 22 / 29 ms | 37 | 0 |

- Ramp: all 409 failures are `429 Too Many Requests` from the app's own limit on plan generation (the old 436 were the same), not overload.
- 300-patient spike: server CPU still touches 100% (p95 99.5%) but nothing fails.
- Weight burst: 126 first-time weight logs, all succeeded, slowest 29 ms. Old run: the server was blocked by plan regeneration. The new run backdates the patients 40 days so each first log passes the 28-day rule.

## Weekly cron `complete-expired-plans`
- Alone: 58 s before, about 8 s now (1,000 patients, 0 failed).
- While 11 req/s of steady traffic ran: 12.4 s (the same job took 44 s under traffic before the fix). Steady traffic during it stayed at 86 ms slowest 5%, 190 ms slowest 1%, 0 errors.

- Log weight and update weight now answer 409 in this sequential test (28-day rule), so their old 244 and 750 ms are not comparable. The success path is the weight burst above.
- Of the 19 endpoints never timed, 3 are now timed (`adjust`, weekly-plan `approve`, admin audit logs). 16 stay untimed: two-factor login (8), Google sign-in, email links (3), delete account, update/delete plan, edit/delete meal log, onboarding. They need email, Google or Firebase, or would break the test data.
- Still no meaningful time for combo swap and `POST /doctor/recipes` (the test input is rejected with 422), and recipe lookup returns 503 without Gemini.

## What this does not tell us
- Docker's CPU limit is not Cloud Run's real CPU: treat times as about plus or minus 30%.
- Database pool was 5+5 (assumed); the code default is 20+20 and the real staging value is unknown. "DB pool at 9 of 10" showed up in most runs.
- The database was on the same machine (0.09 ms round trip); real cloud is 1 to 2 ms.
- Habit learning adds about 5 to 9% to plan generation cost (measured separately, see `HABIT_SIMULATION_2026-10-28.md`).
